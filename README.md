# Stanfordos Mobile

A cross-platform mobile application for the Stanford SMS/LMS platform, built with **React Native, Expo, TypeScript, and Expo Router**.

The mobile app will connect to the existing Spring Boot API and PostgreSQL-backed platform in [MAROOTS/stanford-sms-lms](https://github.com/MAROOTS/stanford-sms-lms). This is a **separate sibling repository**; it does not replace or restructure the backend repository.

## Project decisions

| Area | Decision |
|---|---|
| Platforms | Android and iOS |
| Framework | React Native + Expo + TypeScript |
| Navigation | Expo Router |
| Backend | Existing Spring Boot REST API |
| Database | Existing PostgreSQL database; mobile does not connect directly |
| User scope | All backend-supported roles |
| Roles | ADMIN, TEACHER, STUDENT, PARENT, LIBRARIAN, ACCOUNTANT, PLATFORM_ADMIN |
| Notifications | Push notifications, with in-app notification centre |
| Offline | Read-only cached data |
| Repository | Separate sibling repository |

There is deliberately **no STAFF role** in the mobile role model. The app must reflect the backend's actual `UserRole` enum.

## Quick start

The repository currently contains the project documentation. When implementation begins, scaffold the app with an Expo Router TypeScript template:

```bash
npx create-expo-app@latest . --template
npx expo install expo-secure-store expo-notifications expo-device expo-constants
npm install axios @tanstack/react-query
npm install react-hook-form zod @hookform/resolvers
npm install lucide-react-native
```

Choose the Expo Router TypeScript template when prompted. Confirm package compatibility with the Expo SDK generated by the current Expo CLI; do not pin arbitrary versions from an older guide.

Create a local `.env` from `.env.example` (to be added with the app scaffold):

```dotenv
EXPO_PUBLIC_API_URL=https://your-staging-api.example.com
EXPO_PUBLIC_APP_ENV=development
```

Only public configuration belongs in `EXPO_PUBLIC_*` variables. Never put signing keys, API secrets, database credentials, or private push credentials in the mobile bundle.

## Important integration gates

1. Mobile login needs an explicit, server-validated school/tenant identifier. The existing web authentication flow derives tenant context from the request Origin, which native clients cannot safely reproduce by spoofing headers.
2. Student marks retrieval has a documented self-ownership authorization gap that must be fixed and tested before exposing marks in the app.
3. Parent marks and report-card access need explicit backend authorization and routes before those screens are enabled for parents.
4. Push registration requires backend device-token registration and revocation endpoints.
5. Offline mode is strictly read-only. Attendance, marks, fees, submissions, account changes and all other mutations require a live authenticated connection.

See the detailed documents before implementing any feature.
